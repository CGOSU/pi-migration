# Pi 全局规则

以下规则适用于所有项目；项目根目录 `AGENTS.md` 可补充更具体约定。

1. **按既定需求做最小实现**
   目标明确时直接推进，复用项目现有架构、命名、依赖和调用方式，自主决定普通工程细节。只修改实现当前目标所必需的内容，不顺手重构、清理或增加假想功能。当前改动直接涉及的规范修复及必要的直接调用方迁移，不视为无关扩展。

2. **区分合理假设与关键事实**
   缺少次要信息时，可做最小、可替换的合理假设继续推进；对结果有实际影响的假设和未确认项必须披露。涉及权限、身份、金额、支付、安全、生产数据或不可逆操作的关键事实，必须核实，不得靠猜测补齐；可先完成不受影响部分。

3. **区分业务决策与工程选择**
   按用户已确认的需求和契约执行，实现方案等普通工程选择不重复请求确认。需要新增或改变尚未确认的业务规则、公共契约、权限、业务数据规则或用户路径时，先确认；恢复已有契约或明确预期的 Bug 可直接修复。

4. **保持真实结果与错误语义**
   真实接口、权限、解析或依赖失败，不得伪装成成功或无数据；不得用 mock、默认值或旧数据冒充真实生产结果。临时实现、占位和 fallback 必须明确边界，不得描述为已经完成的真实链路。

5. **验证按需，范围最小**
   按用户要求、项目规则和已确认任务的验收标准执行验证，选择覆盖本次改动风险的最小相关范围。纯静态改动默认仅做静态核对；行为变更和 Bug 修复按适用规则进行必要的针对性验证。不默认运行全量测试、构建、启动服务或调用真实接口。只报告实际执行的检查及结果，不把未验证描述为通过。

6. **页面相关 MCP 按需使用**
   不得仅因新建页面、页面主体大幅重构或改动范围较大，就自动连接或调用页面设计、调试相关 MCP；改动规模本身不是使用 MCP 的依据。
   仅在用户明确要求，或完成已确认任务确实需要 MCP 提供的设计资料、资产、浏览器运行状态或操作能力，且项目现有本地工具无法满足需求时，才使用相应 MCP。
   是否执行页面验证仍遵循“验证按需，范围最小”规则。本条不额外要求启动浏览器、dev server 或其他验证流程；不使用 MCP 不代表页面已验证，未执行的验证不得宣称通过。

7. **保护敏感信息和外部状态**
   不泄露密钥、凭据、`.env`、连接串、token 或未脱敏生产数据。任务完成并通过适用检查后，默认自动创建中文 commit，只提交明确归属于本任务的改动；若已有或暂存改动无法安全区分，先暂停提交并说明。push、发布、部署、生产写入、删除/迁移真实数据、通知、付费或其他难恢复的外部操作，未经用户明确要求不得执行。

## 任务执行策略

### 微修改路径（Fast Path）

仅当任务满足以下条件时使用：

- 修改目标明确，可直接定位到具体文件、符号或文本。
- 属于小型业务代码修改。仅修改与问题直接相关的业务实现，不新增或修改 Test 用例、断言及其他非业务相关代码。预计不超过 5 个文件、20 行代码。
- 属于文案、颜色、尺寸、间距或非行为性展示常量等确定性修改。
- 不涉及数据结构、依赖、系统架构或业务逻辑调整；字段名称修改及字段映射变更不受此限制。
- 任务整体局部、低风险且可逆。
执行：

1. 直接定位目标
2. 只读取完成修改所需的最小上下文
3. 立即修改
4. 只做必要的静态核对；用户、验收标准或项目规则明确要求运行验证时，执行最小相关检查。

限制：

- 不创建 `task_workflow` 或额外书面实施计划
- 不探索无关文件
- 除非无法定位，否则不进行全项目搜索
- 不启动子 Agent
- 不主动重构
- 除非修改可能影响它们，否则不运行全量 test/build/typecheck
- 不为确认已经明确的信息重复读取文件
- 不在修改后反复 review

Fast Path 只修改明确目标及保持一致性所必需的直接关联内容，不为留痕、汇总、规划、发布或知识沉淀同步其他文件和外部状态；仓库一致性要求更新直接关联的测试、快照或生成产物时，仍须一并更新。

Fast Path 不为判断是否需要留痕而预读项目状态、决策、会话或陷阱文档；仅在任务直接依赖其中事实或产生需要记录的新事实时，定向读取对应文档。

用户明确要求和项目级规则优先于本节。若任一适用条件不再满足，退出 Fast Path，按正常流程处理；涉及新增或修复行为时，仍须遵循项目规则执行针对性测试和验证。

## 函数与方法设计

### 结构化校验结果

- 验证/解析外部输入时，优先返回结构化 Result，而非 boolean、null、undefined 或笼统异常。成功返回规范化后的值；失败返回可区分的错误 code 和明确 message。不同失败原因（缺失、类型、格式、范围、精度、溢出等）应尽可能分别表达，便于 UI 展示、日志和调用方处理。
- 本要求同时适用于新增函数和修改既有函数；若既有返回值不符合要求，直接调用方应同步迁移到 Result，调用方数量不构成保留违规返回值的理由。
- 只有已确认的外部发布契约或用户明确要求兼容旧返回值时，才先确认兼容方案；仓库内部函数及其直接调用方默认一并调整。与“影响最小/避免扩大范围”冲突时，本条优先。

### 返回值设计

- 返回值应完整表达调用结果；存在多种失败原因时使用结构化结果（如 Result / discriminated union），避免仅用 boolean、null、undefined 等丢失失败信息

### 参数设计

- 参数应语义明确，外部不可信输入先校验、解析和规范化再进入业务逻辑；避免用 null、空字符串、默认值等掩盖缺失或错误输入。

### 错误处理

- 校验失败应尽可能给出具体、可区分的原因（如缺失、类型、格式、范围、精度），而非笼统的“参数错误”
- 预期的业务失败优先使用显式结果表达，预期业务失败与程序异常应分开处理

## 禁止低收益测试和断言（Test Value Gate）

### 适用范围

目标是避免测试和断言锁定纯文案、样式和实现细节，减少执行时间及后续维护成本。测试和断言的目的，是降低真实回归风险，而不是提高测试数量、覆盖率或制造“完成感”。

### 硬性约束

#### 默认不测试和不断言

以下内容默认属于低收益测试和断言

- 纯展示：文本、文案、标题、提示语、其他文案
- CSS、样式、布局、动画
- DOM 结构、标签、元素数量
- 简单渲染与组件存在性
- snapshot
- getter / setter、常量、枚举、简单字段映射
- 类型系统已保证的行为
- 简单透传、包装函数、纯 CRUD、纯转发 Controller / Repository
- 第三方库与框架自身行为
- mock是否调用、调用次数、调用顺序

#### 优先测试：

- 文本仅在其内容本身属于业务契约、数据结果或关键用户反馈时断言，优先断言最终业务结果，而不是实现过程
- 权限与安全
- 核心业务规则
- 复杂状态流转
- 边界条件
- 数据一致性
- 幂等、重复提交、并发
- 历史 Bug
- 公共 API 行为
- 高风险错误处理

## 完成输出

简单任务完成后只需说明：

- 实际改了什么；
- 有实际影响的假设或未确认项；
- 必要的未处理事项。

只报告实际执行的检查及结果；未执行的测试、构建或真实业务验证，不得描述为已经通过。
